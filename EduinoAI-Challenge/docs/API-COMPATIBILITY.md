# API 호환 규격서

이 문서가 챌린지 양산의 규격서다. **여기 적힌 API 는 시뮬레이터와 실물 교구에서 같게 동작한다.**
표에 없는 것은 시뮬에서 막히며, 에디터가 이유를 함께 표시한다.

시뮬은 고정 10ms tick 결정론 엔진이다. 두 계층은 같은 물리 모델(`setMotorPwm`) 하나로 모이므로
어느 계층으로 짜든 결과가 완전히 같다(검증: 위치·헤딩·랩타임 차이 0).

## 계층

| 계층 | 용도 | 여는 방법 |
| --- | --- | --- |
| 기본 (에듀이노 SDK) | 처음 배우는 학생 | 매니페스트 `allowed_api` 에 기본 API 를 넣는다 |
| 심화 (실물 배선) | 실물 .ino 를 그대로 옮길 때 | `allowed_api` 에 `pinMode`/`analogWrite`/`digitalWrite` 를 추가한다 |
| 카메라 (모드2 색상인식) | 색을 보고 판단하는 과제 | `allowed_api` 에 `camera*` 를 추가한다. `scene.markers` 가 함께 있어야 한다 |
| ML (학습한 모델로 추론) | 카메라로 보고 분류하는 과제 | `allowed_api` 에 `ml*` 를 추가한다. `ml` 설정이 함께 있어야 한다 |
| 시리얼 | 디버깅 | 언제나 열려 있다. `allowed_api` 와 무관하다 |

## 지원 API

| API | 계층 | 동작 | 실물 대응 |
| --- | --- | --- | --- |
| `setMotor(left, right)` | 기본 | 좌·우 PWM 지정. -255~255, 음수는 역회전 | 바퀴마다 핀 두 개에 값을 쓰는 것과 같다 |
| `stop()` | 기본 | `setMotor(0, 0)` | 네 핀 모두 0 |
| `moveForward(speed)` | 기본 | `setMotor(s, s)`. 인자 생략 시 킷 기본 PWM | 동일 |
| `moveBackward(speed)` | 기본 | `setMotor(-s, -s)` | 동일 |
| `turnLeft(speed)` | 기본 | `setMotor(-s, s)` — 제자리 스핀 | 동일 |
| `turnRight(speed)` | 기본 | `setMotor(s, -s)` — 제자리 스핀 | 동일 |
| `delay(ms)` | 기본 | 현재 모터 상태를 유지하며 시간을 보낸다 | 동일 (10ms 단위로 반올림) |
| `pinMode(pin, mode)` | 심화 | 거동에 영향 없음. 실물 코드 호환용으로 받는다 | 동일 |
| `analogWrite(pin, 0~255)` | 심화 | 그 핀에 세기를 준다. 같은 바퀴의 두 핀 중 한쪽만 올리면 그 방향으로 돈다 | 동일 |
| `digitalWrite(pin, HIGH/LOW)` | 심화 | `analogWrite(pin, 255)` / `analogWrite(pin, 0)` 와 같다 | 동일 |
| `Serial.begin(speed)` | 시리얼 | 시리얼 시작. 속도 값은 받아만 둔다 | 동일 |
| `Serial.print(값)` / `Serial.println(값)` | 시리얼 | 시리얼 모니터 패널에 찍는다 | 동일 |
| `cameraSetTarget(r, g, b)` | 카메라 | 찾을 색 지정 (각 0~255) | 프레임에서 목표색을 고르는 필터 설정에 해당 |
| `cameraFound()` | 카메라 | 목표 색이 시야 안에 있으면 참 | 블롭 검출 성공 여부 |
| `cameraOffset()` | 카메라 | 화면 좌우 위치 -100(왼쪽) ~ 0(가운데) ~ +100(오른쪽) | 블롭 중심의 x 좌표를 화면 폭으로 정규화한 값 |
| `cameraArea()` | 카메라 | 화면에서 차지하는 크기 0~100. 가까울수록 크다 | 블롭 크기 (거리 대용) |
| `mlBegin()` | ML | 학습한 모델 사용 시작. `setup()` 에서 한 번 부른다 | 보드에 올린 모델을 여는 것과 같다 |
| `mlClassify()` | ML | 지금 보이는 장면의 분류 결과. `0`=모름 `1`..`N`=클래스 번호 (N 은 매니페스트가 정한 클래스 최대 개수) | 추론 1회 |
| `mlConfidence()` | ML | 그 결과를 얼마나 확신하는지 `0~100`. 모르면 `0` | 추론 점수 |

### 카메라 모델 (모드2)

| 항목 | 값 | 비고 |
| --- | --- | --- |
| 시야각 | 60도 | 좌우 합. 화면 끝이 `cameraOffset()` ±100 |
| 유효 거리 | 1200mm | 이보다 멀면 검출되지 않는다 |
| 색 허용범위 | RGB 채널당 ±90 | 대상 연령을 고려해 넓게 잡았다. `cameraSetTarget(255, 0, 0)` 이면 주황·분홍 계열까지 잡힌다 |
| 미검출 시 | `cameraFound()`=false, `cameraOffset()`=0, `cameraArea()`=0 | `found` 검사를 빠뜨려도 "오프셋 0 = 직진"으로 읽혀 코드가 안전하게 굴러간다 |
| 검출 대상 | `scene.markers` 의 항목 | 여러 개가 보이면 가장 가까운 하나 |

수치는 전부 엔진(`src/engine/camera.js`)이 소유한다. 매니페스트나 스타터 코드에 손으로 적지 않는다.

### 실물 배선 (심화 계층)

실물 키트는 L298N 의 ENA/ENB 를 쓰지 않는다. **바퀴 하나에 핀 두 개**이고, 두 핀 값의 조합이
방향과 세기를 함께 정한다. 좌우 모터는 극성이 서로 반대로 배선돼 있다.

| 상태 | 오른쪽 (`MOTOR_R_PIN_1`, `MOTOR_R_PIN_2`) | 왼쪽 (`MOTOR_L_PIN_1`, `MOTOR_L_PIN_2`) |
| --- | --- | --- |
| 전진 | `0`, `속도` | `속도`, `0` |
| 후진 | `속도`, `0` | `0`, `속도` |
| 좌회전 | `0`, `속도` | `0`, `속도` |
| 우회전 | `속도`, `0` | `속도`, `0` |
| 정지 | `0`, `0` | `0`, `0` |

같은 바퀴의 두 핀에 동시에 값이 들어가면 실물처럼 **브레이크(정지)** 다.
핀 번호와 어느 핀이 전진인지는 킷 스펙(`src/kits/<kit>.json` 의 `pins`·`wiring`)이 소유한다 —
코드에도 문서에도 번호를 박지 않는다. `HIGH LOW OUTPUT INPUT` 과 핀 이름 상수는 심화 계층을 열면 주입된다.

`#define 이름 숫자` 는 그대로 읽는다. 실물 키트 코드가 핀 번호를 그렇게 적어 두기 때문이며,
학생이 적은 값이 킷 기본값보다 우선한다.
`#include "kit.h"` 한 줄도 그대로 읽고 넘긴다(57-C). 그 밖의 헤더는 막힌다 —
없는 라이브러리를 부르고 되는 줄 알면 안 된다.

**좌우 개별 PWM 은 시뮬이 새로 만든 것이 아니다.** 위 표 그대로, 바퀴마다 제 핀 두 개를 갖고
네 핀이 서로 독립이다. 그래서 왼쪽에 180, 오른쪽에 176 처럼 다른 세기를 주는 일이
실물에서 먼저 되고, `setMotor(left, right)` 는 그 위에 이름만 얹은 것이다.
모터 편차를 맞추는 과제(중급 이상)가 성립하는 근거가 여기다.

다만 근거는 킷 스펙(`pins`·`wiring`)까지다. **펌웨어 스케치는 이 저장소에 없고,
실물 보드에서 좌우에 다른 PWM 을 넣어 직접 재 본 기록도 아직 없다.**
재보기 전까지 이 문단은 배선에서 따라 나오는 이야기이지 실측이 아니다(백로그).

### 시리얼

`Serial.begin` / `Serial.print` / `Serial.println` 은 모든 챌린지에서 열려 있다. 문자열(`"..."`)은
시리얼 출력의 인자로만 쓸 수 있다.

**실물과 다른 점**: 실물에서는 시리얼 출력에 시간이 걸린다(115200bps 에서 한 줄에 1ms 안팎).
시뮬에서는 tick 을 전혀 소비하지 않는다 — 출력을 아무리 많이 해도 랩타임이 달라지지 않는다.
출력 줄이 많아지면 오래된 줄부터 버리고 "N줄 생략" 으로 표시한다.

## ML 계층 — 학습한 모델로 추론

실물은 학습한 TFLite 모델을 보드에 올려 추론한다. 시뮬도 같은 모양의 API 를 쓴다.
학습 자체는 코드가 아니라 워크플로우 단계다 — 실물도 IDE 밖에서 하고, 시뮬도 [학습] 탭에서 한다.
그래서 코드에는 추론 세 개만 열린다.

| API | 뜻 |
| --- | --- |
| `mlBegin()` | 학습한 모델 사용 시작. `setup()` 에서 한 번 부른다 |
| `mlClassify()` | 지금 보이는 장면의 분류 결과. `0`=모름 `1`..`N`=클래스 번호 (N 은 매니페스트가 정한 클래스 최대 개수) |
| `mlConfidence()` | 그 결과를 얼마나 확신하는지 `0~100`. 모르면 `0` |

| 항목 | 값 |
| --- | --- |
| 특징값 | 3x3 칸 RGB 평균 27개 + 밝기 히스토그램 8구간 = 35개 정수 |
| 분류기 | k-최근접 이웃 (k 는 데이터 양에서 자동으로 정해진다) |
| 클래스당 최소 · 권장 · 최대 샘플 | 5 · 10 · 30장 |
| 정확도 표시 | LOOCV (샘플을 하나씩 빼며 자기 자신을 맞혀 본다) |

클래스 이름은 매니페스트의 `ml.classes` 가 소유한다(엔진은 개수만 안다).
`ml` 설정이 없는 챌린지에서 이 API 를 부르면 다른 계층과 똑같이 "열려 있지 않은 API" 로 막힌다.

시뮬의 분류기는 신경망이 아니라 브라우저 안에서 도는 결정론 분류기다.
같은 샘플셋이면 담은 순서가 달라도 언제나 같은 모델이 나온다(모델 해시로 확인한다).
샘플 사진은 특징값을 뽑는 즉시 버려지고 저장·전송하지 않는다.

## 카메라 말고는 센서가 없다

실물 킷에 거리센서·초음파·라이다가 없다. 그래서 시뮬에도 그런 API 를 두지 않는다.
스마트시티의 보행자·차단기·신호등도 **눈으로 보고 판단하는 것**이지 읽어 오는 값이 아니다.

| 시뮬의 장치 | API 인가 | 학생이 아는 방법 |
| --- | --- | --- |
| 신호등 | 아니다 | 카메라로 보고 학습한 모델이 분류한다 |
| 보행자 · 차단기 | 아니다 | 같다. 학습 샘플에 담아야 알아본다 |
| 판단 지점 · 구간 | 아니다 | 화면 위 안내 띠와 아래 코스 진행바로 보여 주기만 한다 |
| 배경 보행자 | 아니다 | 인도만 걷는다. 판정에도 충돌에도 관여하지 않는 배경이다 |

판단 지점의 정답은 매니페스트의 `scene.situation` 이 정한다 —
신호 색과 "지금 카메라에 보이는" 장애물을 합쳐 정지 · 서행 · 진행 중 하나를 낸다.
합성 우선순위도 장애물별 요구 행동도 전부 매니페스트가 소유한다.
카메라에 보이지 않는 장애물은 정답을 바꾸지 않는다 — 못 본 것을 틀렸다고 하지 않기 위해서다.

### 코스 대본 (43차)

스마트시티의 여섯 상황은 제 주기로 도는 시계가 아니라 **대본**이다.
상황이 시작되는 시점은 tick 이 아니라 RC카의 접근 거리(`script.trigger_mm`)로 정하고,
시작한 뒤에는 tick 으로 흐른다. 거리로 시작하므로 속도를 바꿔도 같은 자리에서 같은 상황이
벌어지고, tick 으로 흐르므로 멈춰 선 학생 앞에서 보행자가 얼어붙지 않는다.
대본·요구 행동(`requires`)·충돌 거리(`hit_mm`)는 전부 매니페스트가 소유한다.
이것도 API 가 아니다 — 학생은 여전히 카메라로 보고 판단할 뿐이다.

### 규칙 위반 (40차)

`signal_ignored` · `pedestrian_hit` · `gate_hit` · `slow_violation` 네 가지로 나뉜다.
종류별 페널티·충돌 거리·피할 기회 시간은 `rules.violations` 가 소유한다.
계기에는 합 하나만 보이고, 결과와 과제물에 종류별 내역이 나온다.

## 챌린지를 만들 때

1. `allowed_api` 로 계층을 고른다. 처음 배우는 챌린지는 기본 계층만 연다.
2. 스타터 코드의 수치는 직접 쓰지 말고 `{{kit.drive.max_speed_mm_s}}` 같은 템플릿으로 쓴다.
   로더가 킷 스펙과 파생값으로 채우므로 킷이 바뀌어도 어긋나지 않는다.
3. `rules` 로 이탈 허용 횟수와 제한 시간을 정한다.
